How Foundry IQ knowledge graphs work

Foundry IQ can store your documents twice: as text chunks with vectors, for finding passages, and as a graph of entities and relationships, for counting and connecting facts. This guide explains both from the ground up, using the 246-document Kestrel Consulting corpus we built and measured. Part 1 explains the ideas; part 2 shows the exact configuration: ontology, knowledge source, grounding commands, knowledge base and GQL requests.

01One question, two ways

Take the question "How many projects has Amira El Idrissi worked on?" The answer is 7, but no single document says so. Each project's own documents mention her.

That's the core idea behind Foundry IQ knowledge graphs. Everything else in this guide covers how the graph gets built, how it's queried, and where it breaks.

02Graph basics

A graph is a set of nodes (things) connected by edges (relationships). In a knowledge graph the nodes are entities, such as a person, a project or a customer, and the edges say how they relate.

The smallest unit: a triple

Every fact in the graph is a triple: subject, predicate, object. It reads like a short sentence.

Triples connect into a network

Multi-hop: following a chain of edges

Words you'll see a lot

node · entity

A thing

Has a type (label) such as Person and an id. In Foundry IQ it also has a display name.

edge · relationship

A typed, directed link

Has a predicate such as workedOn, and points from subject to object.

property · literal

A plain value

Text, a number or a date attached to a node: "38% of claims auto-triaged". It's not another node.

03Vector search basics

The other half of Foundry IQ is the familiar RAG index. Documents are cut into chunks. Each chunk becomes an embedding: a list of 1,536 numbers that places its meaning as a point in space. Chunks about similar things end up close together.

Foundry IQ doesn't use vectors alone. A typical query is hybrid:

  • BM25 keyword search: exact words, such as "CR-07".
  • Vector search: meaning, such as "budget overrun" matching "15% over the fixed price".
  • A semantic reranker: it reads the combined top results and reorders them by how well they answer the question.

It's a strong baseline. In our tests, simply returning 10 chunks instead of 5 took plain RAG from 42% to 62% correct.

04Why you need both

The two representations answer different kinds of questions. Foundry IQ keeps them side by side, built from the same documents in one ingestion run.

chunk index · text + vectors

Good at "what does it say"

  • Specific facts in one place: "final cost of Claims Triage"
  • Dates, amounts, reasons, narrative
  • Anything the ontology didn't model

Weak at completeness: counts, "all of", "none of".

graph index · triples

Good at "how is it connected"

  • Counting and listing: "how many projects used Databricks"
  • Multi-hop paths: "who worked with Kevin at two employers"
  • Negatives, when the graph is complete: "did Bram ever work for Mediva?"

Weak at detail: only knows what the ontology asked it to extract.

They stay linked. Every triple remembers the chunk it came from (its provenance). A graph answer can point back to the passage that supports it, and a strategy can combine graph rows with passages in one answer.

05What you need to build a graph

Seven ingredients. The blue ones are required for any entity graph; the grey ones are optional but changed our results a lot.

source

Documents in Blob Storage

Text-based files in a container. Graph extraction needs blob soft delete on and versioning off before the first run. ADLS Gen2 and permission (ACL) ingestion aren't supported for graphs.

service

A Foundry IQ search service

Ours is Serverless in West US 3: pay per use, scales to zero. It must support API 2026-11-01-preview.

schema

An ontology

A JSON-LD file listing the entity types and relationships to extract. It decides what the graph can answer, and it's fixed after creation.

model

A chat model for extraction

Reads every chunk and writes triples. Microsoft recommends gpt-5.6-luna. One call per chunk, so cost scales with chunk count.

model

An embedding model

For the chunk vectors, here text-embedding-3-small (1,536 dimensions). The same model embeds questions at query time.

optional · entity resolution

A grounding list

Known entities with ids and aliases, so "Amira", "AEI" and "Amira El Idrissi" become one node. Must be set up before the build.

optional · plugin builds

A cache storage account

The Foundry IQ skills plugin requires a separate StorageV2 account as its ingestion cache.

permissions

Managed-identity roles

The search service's identity reads the blobs (Storage Blob Data Reader) and calls the models (Cognitive Services OpenAI User). No keys needed.

tooling

REST API or the skills plugin

Entity graphs are API-only in this preview; the portal shows the objects but not the graph settings. The plugin adds guided builds, grounding and a Playground UI.

Then one API call, PUT /knowledgesources with a graphExtraction block, starts everything.

06How the graph is built

That single call creates five objects. Together they form a pipeline that runs every time the indexer runs: once at creation, then daily for new or changed blobs.

Inside the extraction step

The triple extraction skill is the only genuinely new piece. Its generated definition shows three stages:

  • Extract: the chat model reads a chunk and the ontology and proposes triples (temperature 0.3, low reasoning effort).
  • Align: maps the proposed relationships onto the ontology's predicates, and drops those below a confidence of 0.5.
  • Ground: if a grounding index is configured, resolves each entity name to a known id. Without one, entities get ungrounded: ids derived from their text.

08Grounding: one entity, one node

Documents name the same thing many ways. Without help, extraction turns every surface name into its own node. Our ungrounded graph had 46 Person nodes for 25 real people.

The catch: fuzzy matches cross types

One of the lookup steps is a fuzzy text search, and it doesn't appear to check the entity type. Free-text values that share a word with a known name get that entity's id:

"Field crew capacity"grounded to →project:P5 · Bed Capacity Dashboard
"SCADA data only reachable through the OT DMZ" (AquaNova)grounded to →project:P10 · Verhaeghe Line Sensor
"about 160 m"grounded to →org:mediva

With issues as entities (v2), 5% of grounded edge ends were cross-type merges, and some projects disappeared from type-filtered queries. Turning issues into text properties (v3) fixed the counts, but the lookup still runs on text values: 387 issue and outcome texts still got an entity id.

Rule of thumb

Ground only things with stable names (people, customers, products), and keep free text out of entity types. Then check the graph directly: count nodes per type against what you know is true.

09How a graph is stored

There's no separate graph database. The graph index is an ordinary search index with one document per triple. A graphProfile on the index tells the engine which fields are the subject, predicate, object, ids and provenance, and that turns the rows into a traversable graph.

Each row also carries:

  • Confidence scores: they were all 0 in our ungrounded graph, and grounding filled them in (mean 0.71).
  • Provenance: chunk_id and parent_id point to the passage and the document the triple came from.

Because it's a normal index, you can open it in the portal's Search explorer and see the triples, as in our walkthrough screenshots.

10Asking a graph: GQL

Graphs are queried with GQL, ISO/IEC 39075:2024, the first new ISO database language since SQL. You draw the shape you're looking for, and the engine finds every place it occurs.

MATCH (p:Person)-[e]->(j:Project)
WHERE e.predicate = 'workedOn' AND p.id = 'person:amira'
RETURN count(DISTINCT j) AS projects, COLLECT_LIST(DISTINCT j.name) AS names

Multi-hop is just a longer pattern. The Kevin and Jonas question from section 2 becomes two people meeting on the same project, with the result grouped per consultant.

You rarely write GQL yourself. Ask a knowledge base a question and it generates the GQL with a language model. You can also send your own GQL to POST /indexes('<graph-index>')/docs/search.graph, which is what our own agent does.

11What happens at query time

A knowledge base sits on top of one or more knowledge sources. When you send it a question, it plans, chooses tools, runs them, and returns extractive data: the passages and graph rows it found.

Where it went wrong in our tests

  1. The rewrite adds assumptions. "Amira's projects" became "Kestrel Consulting projects that Amira worked on", and the generated GQL then filtered on a relationship that didn't fit.
  2. The query generator sees the schema, not the data. It picked workedOn for a customer contact, and filtered name = 'fortalis verzekeringen' where the graph also said "Fortalis".
  3. An empty result is a success. A wrong query and a true "no" look identical: both report outcome: Success with 0 rows, and there's no retry.

12Four ways to retrieve

We compared four retrieval strategies on the same index. In every case the same answer model writes the final answer, so only the retrieval differs.

Plain RAG

hybrid search
question→BM25 + vector + rerank→top 5 or 10 chunks→answer
~1 s
~2.5–5k tokens

Retriever 1

queryType: agentic

~40k engine tokens

Entity knowledge base

question→planner→NL → GQL→graph rows+passages→answer

Own GQL agent

our loop, two tools
question→agent with ontology + entity names⇄run_gql⇄search_text(≤8 calls)→answer
~12 s
~20k tokens

language model stepchunk indexgraph index

The own agent fixes the three weak spots of the managed path:

  • It sees the data: the prompt includes the entity names that actually exist in the graph.
  • It mixes tools freely: it can run graph queries and text searches in the same investigation.
  • It treats 0 rows as a signal: if a query returns nothing, it checks whether a filter was too strict and retries.

It's the slowest strategy, but the most consistent.

13Topic graphs

A topic graph needs no ontology. It clusters the chunk vectors into topics, so similar passages group together, and asks a model to name each cluster. At query time it can diversify: instead of the closest matches, which often all come from one topic, it takes good matches from several topics.

14What we measured

We ran 24 questions with known answers over the 246-document corpus: lookups, counting, negatives, multi-hop, look-alike names, timelines and synthesis. A judge model scored whether each answer was correct, and what share of the required facts it contained (fact recall).

Read these as directions, not rankings. With 3 to 5 questions per category, runs vary a lot. Retriever 1 scored 67% in one run and 46% in the next with the same setup. Differences under about 15 points aren't meaningful here.

What held up across runs

Graphs win at counting and paths

Counting went from 1/5 with RAG to 4/5 with graph strategies, consistently. A clean graph answers "how many" exactly.

The question-to-GQL step is the bottleneck

The same graph scored 42% through the managed knowledge base at low effort, and 67% through our agent. Raising the knowledge base to medium closed most of that gap.

Simple levers are big

Twice the passages lifted plain RAG by 20 points in about 1 second. Graph strategies take 10 to 20 seconds and up to 20 times the tokens.

Grounding fixes the graph, not yet the score

Node counts became exact, but end-to-end scores moved within the noise. Every LLM step between graph and answer adds its own variance.

The one-line version

A knowledge graph is a data product, not a switch. It pays off when you need exact counts, lists or connections across many documents, and when you invest in the ontology, grounding and checking the graph against the truth.

The file format the plugin requires

Our first two versions used an ex: prefix and were sent to the service by hand, which accepted them. For v3 we built through the Foundry IQ skills plugin, and its ontology-consume check only passes a canonical profile:

{ "@context": { "owl": "http://www.w3.org/2002/07/owl#",
                "rdfs": "http://www.w3.org/2000/01/rdf-schema#",
                "xsd": "http://www.w3.org/2001/XMLSchema#" },     // exactly these three
  "@graph": [
    { "@id": "https://schema.search.azure.com/entities#",
      "@type": "owl:Ontology", "owl:versionInfo": "kestrel-v3" },   // header first
    { "@id": "https://schema.search.azure.com/entities#Organization",  // full IRIs, no ex:
      "@type": "owl:Class", "rdfs:label": "Organization", "rdfs:comment": "…" },
    …                                                              // classes, then object, then datatype properties, each sorted by id
    { "@id": "https://schema.search.azure.com/entities#achieved",
      "@type": "owl:DatatypeProperty",
      "rdfs:domain": { "@id": "…#Project" },
      "rdfs:range":  { "@id": "http://www.w3.org/2001/XMLSchema#string" },  // text, not a node

19Step 3 · Grounding, command by command

To ground a graph, the knowledge source gets one more setting:

"graphExtraction": { …, "grounding": { "kind": "searchIndex", "index": { "indexName": "grounding-kestrel-v3" } } }

That index has to exist first, in the right shape, and carry the graph name of the build that will use it. The portal has no screen for this, so we used the CLI of the Foundry IQ skills plugin. It builds the index, checks it, and doesn't write anything until you approve a plan.

The input: a list of entities you already know

id,name,type,aliases

This file comes from groundtruth/entities.csv. In a real setting it would be your HR system, CRM and project list.

The commands, in order

  1. Connect the existing resources. entity-graph-provision connect … --search-name srch-kestrel-r1 --storage-name … --use-system-identity, then connect-apply. Writes build-args.json with the endpoints, model deployments and identity that every later command reuses. It refused at first because publicNetworkAccess and networkAcls.defaultAction were unset. Unset already means public, so we set them to those same values: nothing was opened further.
  2. Check the service. grounding-provision doctor --build-args build-args.json: roles, endpoints and API version.
  3. Validate the ontology. ontology-consume check ontology-v3.jsonld: the canonical format from section 17.
  4. Plan the graph build. entity-graph-build plan --ontology inline_jsonld --ontology-path ontology-v3.jsonld --grounding-index grounding-kestrel-v3 …. A dry run. It fixes the graph name, entity-managed-03116d12fb395249, a generated name. The grounding index has to carry exactly this name.
  5. Plan the grounding index. grounding-build plan --file entities.csv --graph-name entity-managed-03116d12fb395249 --index grounding-kestrel-v3. Also a dry run, ending in an approval card. The index name must start with grounding-.
  6. Create and load it. grounding-build apply --plan-id pln-… creates the index with a POST, so it never overwrites an existing one, and loads one label row per name and alias: 144 rows from 67 entities.
  7. Check that it's ready. grounding-consume ready --index grounding-kestrel-v3 --graph-name entity-managed-03116d12fb395249 confirms the schema and the graph name match.
  8. Build the graph. entity-graph-build apply --plan-id build-plan-… --confirm-writes --wait creates the knowledge source with grounding set, plus the pipeline from section 18, and runs it.
  9. Verify and publish. entity-graph-build verify runs read-only checks (628 chunks, 3,578 triples) and measures grounding coverage. publish --keep-current then marks the build as published without replacing the existing graphs. Its knowledge base is entity-kb-03116d12fb395249.

What the grounding index contains

The grounding index is itself a small graph index: one rdfs:label triple per name. These are Amira's three rows:

{ "subject_id": "person:amira", "subject_type": "Person", "predicate": "rdfs:label", "object": "Amira El Idrissi",
  "graph_name": "entity-managed-03116d12fb395249", "edge_confidence": 1.0, "chunk_id": "grounding" }
{ … "predicate": "rdfs:label", "object": "AEI" … }
{ … "predicate": "rdfs:label", "object": "Amira" … }

Lookups filter on graph_name, so an index loaded with a different graph name matches nothing, without any error. chunk_id: "grounding" is a fixed placeholder, because these rows don't come from a passage.

20Step 4 · The knowledge base and its retrieve call

A knowledge base is the query side. It names the knowledge sources, the model that plans, and instructions for that model. This is the one we wrote for the ungrounded graph:

PUT /knowledgebases('kestrel-entities-kb')?api-version=2026-11-01-preview
{ "name": "kestrel-entities-kb",
  "knowledgeSources": [ { "name": "kestrel-entities-ks" } ],
  "models": [ { "kind": "azureOpenAI", "azureOpenAIParameters": { "deploymentId": "gpt-5.6-luna", … } } ],
  "outputMode": "extractiveData",                   // return what was found; we write the answer ourselves
  "retrievalReasoningEffort": { "kind": "low" },    // default; each request can override it
  "retrievalInstructions": "Use graph_search for questions about who worked on what, which projects used a
    technology, counting, comparisons across customers … Graph schema facts: every Project in this graph is a
    Kestrel Consulting project, so never filter on 'Kestrel Consulting'. deliveredFor always points to the CUSTOMER …
    match names with CONTAINS on the most distinctive part … and count DISTINCT entities. Customer contacts link to
    projects with sponsors, productOwnerOf or contactFor; consultants with workedOn or managedProject." }

Our only lever on the generated GQL

The planner reads it, and it can carry schema facts that the ontology alone doesn't make obvious. It helped with the "never filter on Kestrel" mistake. It didn't make the query generator use CONTAINS, as the GQL further down shows.

The knowledge bases the plugin made use answerSynthesis, with answerInstructions to cite every claim. We ask for extractiveData on every request, so that the same answer model writes the answer for every strategy.

Why 5 and not 7: the GQL it wrote

The activity doesn't always include the GQL; this call didn't. An earlier evaluation run of the same question did log the generated query:

MATCH (p:`Person`)-[r:`workedOn`]->(pr:`Project`)
WHERE LOWER(p.name) = LOWER('Amira El Idrissi')
RETURN DISTINCT pr.name AS project_name, type(r) AS relationship, r.confidence AS confidence

Grounding gave every mention of Amira the same id, person:amira. But a node's name is still the name used in each passage, and this query matches the full name exactly. The two projects where she's only called "Amira" or "AEI" fall outside it. Filtering on p.id = 'person:amira' finds all 7, as the next section shows. The query generator sees the schema but not the ids, so it can't write that filter.

21Step 5 · Query the graph directly with GQL

33 ms · 0 tokens

Takes GQL you write. It returns exactly what you asked for, using ids, DISTINCT and aggregates. But someone has to write the query: you, your code, or your own agent.

The GQL that works on these graphs

PatternExample
Node label = entity type(p:Person), (j:Project)
Relationship = edge property-[e]-> with e.predicate = 'workedOn', or e.predicate IN ['sponsors','productOwnerOf']
Grounded graph: filter on the idp.id = 'person:amira'
Ungrounded graph: match a distinctive part of the namep.name CONTAINS 'Idrissi'
Multi-hop(k:Person)-[e1]->(j:Project)<-[e2]-(c:Person)
Counting and listscount(DISTINCT j), COLLECT_LIST(DISTINCT j.name), GROUP BY, ORDER BY n DESC
Shape of the graphMATCH (n) RETURN labels(n) AS type, count(*) AS n GROUP BY type

A query can be at most 2,048 characters and returns at most 1,000 rows. Your identity needs read access to the index (we have Search Index Data Contributor). The Graph Lab app's GQL console sends exactly this request.

23Glossary

Knowledge source
Where content comes from and how it's ingested. A blob knowledge source generates the data source, skillset, indexer and indexes.
Knowledge base
The query side: which sources, which planning model, how much reasoning effort. It's also an MCP endpoint for agents.
Chunk
A piece of a document, here at most 2,000 characters with 200 characters of overlap.
Embedding
A list of numbers (1,536 here) that places a text's meaning in space, so similar texts are close.
Hybrid search
Keyword (BM25) and vector search combined, then reordered by a semantic reranker.
Triple
One fact: subject, predicate, object. Stored as one document in the graph index.
Ontology
The schema of entity types and relationships, as JSON-LD. Fixed after creation.
Object vs datatype property
A relationship to another entity, versus a plain text or number value.
Grounding
Resolving names to canonical ids from a list of known entities, so variants become one node.
Provenance
The link from a triple back to the chunk and document it was extracted from.
GQL
ISO graph query language. Patterns of nodes and edges, with filters and aggregates.
Multi-hop
A question answered by a path through several connected nodes.
Retrieval reasoning effort
How much planning a knowledge base does: minimal, low, medium or auto.
Topic graph
Clusters of similar chunks, used to diversify results across themes.
graphProfile
The index setting that maps fields to subject, predicate, object, ids and provenance, and turns an index of triples into a graph.
Grounding index
A small graph index of rdfs:label rows, one per known name or alias, carrying the graph name of the build that uses it.
Minted id
An ungrounded:v2:… id the skill creates when a mention matches nothing in the grounding index.
search.graph
The endpoint that runs GQL directly on a graph index, with no model involved.
Activity
The step-by-step log a knowledge base returns with includeActivity: planning, graph and text searches, with tokens and times.
